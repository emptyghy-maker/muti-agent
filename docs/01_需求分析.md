# 01 需求分析

## 1. 业务背景与目标

为用户提供「从目的地到完整行程」的一站式规划，并形成**反馈驱动的持续迭代**：
- 用户只需首轮自由表达 + 少量按钮点击，就能得到按天、含预计消费、可点击查看路径的行程；
- 行程**持久化保存、可随时找回、可局部修改**；
- 建立**评价反馈体系**，收集用户真实体感，反哺系统优化（规则参数、提示词、数据）；
- **小范围起步**：先只做江苏的热门城市（南京、苏州），跑通 + 收集反馈，再扩容。

## 2. 用户角色

| 角色 | 说明 |
|---|---|
| 游客（普通用户） | 发起规划、回答问询、确认候选、查看/修改行程、提交评价 |
| 系统运营（本阶段为人工） | 通过反馈数据统计，迭代调整规则参数/提示词/种子数据；本阶段不做管理后台 |

## 3. 功能需求

### F1 目的地选择
- 首期目的地：**南京、苏州**（江苏热门城市），后续按反馈扩容。
- 入口：首页城市卡片；也可在首轮对话中直接说出目的地。

### F2 开场与多轮问询（核心体验）

#### 开场白（固定文案 + 引导提示词）
> 「你好，我是你的旅游攻略智能规划助手，请向我提供一些你的规划想法，让我帮你进行初步规划」
> 提示词示例：「如：想去哪里玩、规划几天旅途、预算范围、喜欢什么类型的景点和美食」

#### 首轮解析 + 缺口分析（防重复提问的关键）
1. 用户首轮自由输入（可能一句话含多个信息：目的地、天数、预算……）。
2. `PreferenceAgent` 解析该输入，**抽取已提到的字段**并打上「已确认」标记。
3. Agent 基于「缺失字段清单」输出**下一步要问的问题**（只问缺失的，绝不重复已确认的）。

**防重复提问的硬机制（规则兜底，不依赖 LLM 自觉）**：
- `TravelPreference` 每个字段三态：`MISSING 未获取 / CONFIRMED 已确认 / DEFAULTED 已默认`；
- 会话中维护 `askedFields` 集合（已问过的字段）；某字段问过但用户答「随意」→ 置 DEFAULTED，不再追问；
- Java 校验：Agent 输出的 nextQuestion 若指向「非缺失字段」，规则直接丢弃，改从缺失清单按优先级取下一个问题——**即使 LLM 想重复问，也会被规则拦下**。

#### 分步问询（一次 1~2 个问题，不做整张问卷）
按三批优先级逐步推进，每步最多问 2 个问题（避免一次问太多惹用户烦）：

| 批次 | 字段 | 优先级理由 |
|---|---|---|
| 第一批（硬约束） | 目的地、游玩天数、总预算 | 直接决定行程骨架与候选数量 |
| 第二批（偏好） | 人数、景点偏好（打卡/娱乐）、美食口味 | 决定候选内容与酒店床位 |
| 第三批（可默认） | 体力水平、酒店细节（档次/性价比）、特殊需求（必去地点） | 可用默认值，不影响骨架 |

#### 前端交互形式（混合式）
- **首轮**：自由文本输入框（配引导提示词）。
- **后续轮次**：Agent 的问题**携带 `options` 选项**（如天数 → `["2天","3天","4天及以上"]`），前端渲染为**单选/多选按钮**，用户点一下即完成回答；同时保留自由输入框（可输入按钮之外的内容）。
- **逐步问，不用问卷**：① 用户自述「一次问很多会嫌烦」；② 逐步问能让 Agent 根据已答内容动态调整后续问题（如天数已定 → 景点候选数量随之确定）。

#### 模糊回答与默认值（防迭代爆炸、省 token）
用户对某些问题「没想好」是常态，策略是**给合理默认值 + 明示 + 一次通过，不追问**：

| 模糊场景 | 默认策略 |
|---|---|
| 预算未定 | 按目的地「人均日消费参考区间」取中位数 × 天数 × 人数，明示「先按 3000 元规划，之后可调整」 |
| 景点类型「都可以」 | 默认「打卡拍照 60% + 娱乐 20% + 休闲 20%」混合 |
| 天数「随便」 | 默认 3 天 2 晚 |
| 体力「不知道」 | 默认「一般」 |

> 目的：预算给大了/给小了反复迭代重生成会白白烧 token；一次默认 + 事后「修改」通道（见 F6）解决，比事前追问体验好得多。

#### 冲突检测与二次确认
若 Agent 发现用户需求存在**需要协调的矛盾**（如「预算 3000」+「想住豪华酒店」），进入 **CONFLICT 状态**，向用户二次确认：
> 「您的预算与酒店要求有点冲突，请选择：① 提高预算到 5000；② 降低酒店档次到舒适；③ 按您的原预算由我推荐最优方案」

### F3 候选集生成（三级，逐级确认）

**第一级：景点待选项**（名称+特色）——依据目的地 + 景点偏好 + 天数（候选数 ≈ 天数×1.5~2）。
**第二级：美食待选项**——按**风味集合**组织（风味 → 店铺名集合 + 其他），依据口味 + 餐饮预算 + 已选景点位置。
**第三级：酒店候选集**（名称+金额+评分）——依据已选景点/美食**坐标聚合中心**就近找 + 酒店偏好（性价比=评分/价格排序，体验=评分排序，预算为硬约束）。

- 候选**必须来自数据库**，LLM 只做筛选排序，输出过 **id 白名单校验**（防幻觉）。
- 每级最多 regenerate（换一批）2 次，防止无休止刷候选浪费 token。

### F4 按天路径规划（核心）
输入：确认的景点/美食/酒店 + 天数 + 总预算 + 路径风格（默认最省事）。

输出：按「第一天/第二天/…」组织的行程文本 + 结构化节点（每天：酒店锚点、景点、饭店、交通节点、休息点、预计消费）。

约束规则：
1. **饭点约束**：午餐 11:30–13:30、晚餐 17:30–19:30 必须有实体餐点；**车程中不推荐用餐**。
2. **操劳程度**：当天/前一天/后一天劳累分联动（详见 03 的 FatigueScorer），超阈值插入休息点（低强度景点，标注「休息点」）。
3. **预计消费**：门票+餐饮+酒店+交通，按天 + 全程；超预算给出降级建议。
4. **首尾衔接**：首日含启程（机场/高铁）、末日含返程。
5. **天气提醒**：生成行程后，若行程以室外景点为主，附一句「如遇雨天，建议改期或替换为室内景点（博物馆等）」（详见 F8）。

### F5 地点超链接 → 路径详情
- 行程中所有地点为超链接；点击任一地点，展示「上一地点 → 该地点」的具体路径（方式/耗时/费用/步骤）。

### F6 行程持久化与修改（结果不能丢）

**持久化**：
- 行程生成完成后即落 MySQL（`t_itinerary`，含 preference_json + plan_json）。
- **「我的行程」入口**：前端行程列表页（按用户隔离），点击进入详情——详情页**从数据库加载**，不依赖 Redis 会话，刷新/重进不丢。
- 规划中途刷新：从 Redis 会话恢复；会话过期（TTL 2h）时提示「会话已过期，已生成的行程可在『我的行程』中找到」。

**修改（局部调整）**：
- 行程详情页提供「调整」入口，用户输入调整诉求（如「第二天太赶，删一个景点」「酒店换成 400 以内」）。
- 走 **ADJUST 修改模式**：携带「原行程 + 调整诉求 + 原偏好」调用 ItineraryAgent 做局部重生成；**不重新走问询、不重新确认候选**。
- `t_itinerary` 保留版本（version + parent_id），每次修改生成新版本，可回退查看历史。

### F7 评价与反馈体系（驱动迭代优化）

目标分两层：
1. **单用户即时优化**：行程页随时可反馈 → 触发「修改模式」。
2. **系统级迭代优化**：聚合反馈数据，人工分析 → 调整规则参数（疲劳阈值/饭点窗口）、提示词、候选排序权重、种子数据。

**反馈入口与内容**：
- 行程页底部：综合星级（1~5）+ 快捷标签（「太赶了」「很满意」「想换酒店」「预算超了」）+ 文字评论。
- 维度评分：节奏（太赶/刚好/太松）、景点满意度、美食满意度、酒店满意度、预算匹配（超支/刚好/富余）。
- **隐式反馈**（自动记录）：候选「换一批」次数、修改次数、重新生成次数——作为「体验摩擦」的信号。

**落地**：`t_itinerary_feedback` 表 + 统计查询接口；迭代期人工分析这些数据，决定优化方向（这正是本项目「先小范围跑，再按反馈升级」的方法论）。

### F8 天气因素（提醒层，非核心决策层）
- 提前几天规划无法准确预知天气 + 概率极小 → **按正常流程推荐**，生成后附天气提醒：「如遇雨天，建议调整出行日期，或替换为室内景点（XX 博物馆）」。
- 数据层预留：`t_attraction.indoor` 标记（室内/室外），供雨天建议引用。
- 进阶预留：未来接天气 API（规划前查目的地未来 N 天天气，雨天自动优先室内景点），本阶段不接真实 API。

## 4. 非功能需求

| 项 | 要求 |
|---|---|
| 性能 | 单轮问询 ≤ 3s；候选集 ≤ 5s；行程流式首 token ≤ 3s |
| 防重复提问 | 字段三态 + askedFields + Java 规则兜底（硬保证） |
| 防 token 浪费 | 默认值一次通过不追问；regenerate 上限 2 次；修改走局部重生成 |
| 持久化 | 行程落库可回看；刷新/重进不丢 |
| 可观测性 | Agent 耗时 + token（trace 框架）；请求日志 |
| 安全 | JWT 鉴权；行程/反馈按用户隔离 |
| 稳定性 | LLM 失败优雅降级；候选为空引导调整偏好 |

## 5. 范围边界（本阶段不做）

- 真实地图导航 API（预留 RoutePlanner 接口）、真实天气 API（预留）。
- 酒店/门票预订支付、多目的地串联、跨境游。
- 管理后台（数据用种子 SQL）；向量数据库/RAG 知识库（城市少，DB+提示词足够）。
- 首期仅南京、苏州两城。

## 6. 验收场景

1. 用户选「南京」→ 首轮输入「带爸妈去南京玩三天，预算 4000，想吃点地道的」→ 系统抽取到【目的地✓、天数✓、预算✓、口味=地道】→ 只追问缺失项（人数、景点偏好等，配选项按钮）→ 三级候选确认 → 生成 3 天行程（第二天劳累分高插入「老门东茶馆（休息点）」；因行程多室外景点，尾部附雨天提醒）→ 点击「夫子庙」看到上一地点的路径方案。
2. 用户答「随意」的字段全部按默认值一次通过，并在行程中标注「已按默认处理」；全程无重复提问。
3. 用户刷新页面后，从「我的行程」找回行程；输入「第二天太赶了」→ 生成新版本行程，可对比旧版本。
4. 用户提交评分「节奏=太赶」+ 评论 → 反馈落库，统计接口可见。
