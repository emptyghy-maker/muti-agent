## 2. 总体分层架构

```
┌───────────── 前端 Vue3 ─────────────┐
│ 目的地选择 → 分步问询(按钮快捷回复) → 候选确认 → 行程时间线/文本 → 路径弹层 → 我的行程/修改/评价 │
└──────────────┬──────────────────────┘
               │ REST + SSE（JWT）
┌──────────────▼──────────────────────┐
│ Controller：TravelController / RouteController │
├─────────────────────────────────────┤
│ TravelOrchestrator（对话状态机：多轮问询/候选/规划） │
│   ├── PreferenceAgent    （偏好收集）          │
│   ├── AttractionAgent    （景点候选）          │
│   ├── FoodAgent          （美食候选）          │
│   ├── HotelAgent         （酒店候选）          │
│   └── ItineraryAgent     （行程规划，核心）     │
├─────────────────────────────────────┤
│ 规则引擎（纯 Java，可测试、可解释）            │
│   ├── FatigueScorer      （操劳程度评分）      │
│   ├── MealTimeChecker    （饭点约束检查）      │
│   ├── BudgetCalculator   （消费汇总/超支检测） │
│   └── RoutePlanner 接口  （两点路径：Simple 实现 + 预留高德实现）│
├─────────────────────────────────────┤
│ 数据层：MyBatis-Plus Mapper（t_destination/t_attraction/t_restaurant/t_hotel/t_itinerary）│
│ 会话层：Redis（travel:session:{id}，多轮中间状态 + 候选集）│
└─────────────────────────────────────┘
```

设计原则：
1. **LLM 做「选与说」，规则做「算与守」**——筛选排序、文案生成交给 LLM；疲劳度、饭点、预算、路径用规则引擎计算，LLM 不许违背硬约束。
2. **候选来自数据库**——LLM 不凭空生成地点（防幻觉）。
3. **全程可观测**——每个 Agent 接入 trace 框架，复用旧项目能力。
4. **反馈闭环**——用户评价 + 隐式信号（换一批/修改次数）回流，迭代期据此调规则参数、提示词与数据。

## 3. 关键选型决策（D1–D6）

### D1 数据来源：本地种子库为主，预留外部数据源接口
- **决策**：景点/美食/酒店数据存 MySQL 种子库（2~3 个热门城市，每城 20 景点/15 美食店/12 酒店，含坐标/价格/评分/标签）。
- **理由**：零外部依赖、可学习、可审计、杜绝 LLM 幻觉地点；规模小，标签 + SQL 检索足够，**不引入向量库**。
- **预留**：抽象 `PlaceDataSource` 接口（本地实现 `DbPlaceDataSource`），未来可接高德 POI 等真实数据源。

### D2 路径规划：接口化，默认简单实现，预留地图 API
- **决策**：`RoutePlanner.plan(fromId, toId)` 接口。
  - 默认实现 `SimpleRoutePlanner`：基于坐标直线距离估算——<1km 步行（5km/h），1~8km 公交/地铁（按 20km/h 折入换乘），>8km 打车（35km/h，起步 12 元 + 2.5 元/km）；输出方式/耗时/费用/模拟步骤文本。
  - 预留实现 `AmapRoutePlanner`：高德地图 Web 服务 API（真实步行/公交/驾车方案），配置开关切换（`travel.route.provider=simple|amap`）。
- **理由**：学习阶段零成本可跑通全链路；架构上支持后续升级真实导航，不影响业务代码。

### D3 会话状态管理：Redis 存中间态，MySQL 存最终行程
- **决策**：多轮问询与候选确认的中间状态存 Redis `travel:session:{id}`（TTL 2h）；行程生成完成后落 MySQL `t_itinerary`（preference_json + plan_json）。
- **理由**：多轮对话天然有状态；Redis 过期自动清理废弃会话；最终结果持久化可回看。

### D4 疲劳度/饭点：规则引擎 + LLM 混合
- **决策**：`FatigueScorer` 算每天劳累分（Σ 景点强度×时长 + 交通时长），`MealTimeChecker` 检查饭点窗口（11:30–13:30 / 17:30–19:30）是否有就餐节点；劳累分超阈值（含前一天/后一天联动）→ 规则引擎**决定插入休息点**（从低强度景点中选）。LLM 只负责在规则给定的骨架之上组织自然语言。
- **理由**：硬约束交给代码保证不被 LLM 违背（旧项目教训：LLM 会编造、会违规），文本质量交给 LLM。

### D5 Agent 划分：5 个 Agent + 工具，状态机编排
- `PreferenceAgent`（问询收集）、`AttractionAgent`（景点候选）、`FoodAgent`（美食候选）、`HotelAgent`（酒店候选）、`ItineraryAgent`（行程规划）；路径规划是工具（RoutePlanner），不是 Agent。
- 编排：`TravelOrchestrator` 维护状态机 `PREFERENCE → ATTRACTIONS → FOODS → HOTELS → ITINERARY → DONE`，支持用户回溯改选择。
- 详见 `03_多Agent设计.md`。

### D6 模型分层（已按反馈更新：PreferenceAgent 升级到 plus）
| 模型 | 用途 | 理由 |
|---|---|---|
| qwen3.7-plus（规划模型） | PreferenceAgent + ItineraryAgent | 需求解析与多约束编排是「质量敏感」环节：解析不准会重复提问（体验红线），编排不准行程不可用 |
| qwen3.8-flash（default） | Attraction/Food/Hotel | 筛选排序任务简单、容错空间大，快且便宜 |

> 升级路径：跑通后用 trace（耗时）+ 反馈数据（满意度）评估每个 Agent；某个 Agent 能力不足时单独换更强模型（Agent 独立绑定 ChatModel Bean，仅改 AgentConfig 一行）。
